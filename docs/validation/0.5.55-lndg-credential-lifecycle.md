# LNDg credential lifecycle — 0.5.55 candidate

Status: draft, pending native Linux integration. Depends on the credential
inspection/authentication helper introduced by the LNbits PR #395. No node was
changed by this implementation.

## Scope and evidence

The catalog pins LNDg 1.11.0, commit
`0fe400029240fc59431b56b6ce47e24b764396b1`. Its actual source calls OpenChannel,
CloseChannel, SendCoins (self-consolidation), SendPaymentV2, UpdateChannelPolicy,
ConnectPeer/DisconnectPeer, SignMessage, VerifyMessage and DeriveSharedKey.
Reducing it to LNbits wallet-only permissions would break supported functions.
The existing permission list is unchanged.

The EN/PT Store card and install confirmation now explicitly describe payments,
on-chain spending, channel open/close and signing authority, outside LOS guards.
A dedicated macaroon is not a spending limit. An RPC allowlist could reduce unused
methods, but SendCoins remains unrestricted as to destination if it is retained.

## Removal design

Only the LNDg removal path changes; ordinary stop/start does not revoke anything.
Before Docker mutation, the broker validates the fixed credential path, its exact
catalog policy, a non-default timestamp-format root, its private enrollment and
LND authentication. There is no caller-supplied root/path or additional Manager
privilege. Unknown, custom, caveated, legacy non-timestamp or unenrolled
credentials require operator review rather than automatic revocation.

After Compose down succeeds, a private broker receipt records revocation intent.
The dedicated root is deleted and its absence verified; the receipt supports
retry after interruption. Only then are the execution snapshot and dedicated
macaroon file removed. Application databases/data and native LND material remain.
An install must then bake a fresh credential through the existing missing-file
path. A reused root after a completed revocation is rejected, not deleted.

All copies under the removed root become invalid. Operators must not share an
App Store credential/root with other applications. Broker enrollment identifies
the credential managed by this app; it cannot prove nobody copied it elsewhere.
Already-uninstalled legacy installations without enrollment are **not** silently
cleaned up. If preflight cannot establish ownership, uninstall reports failure.

## Validation

Baseline focused LNDg tests passed on Windows amd64 before editing. Focused new
tests pass for dry-run, successful removal, preserved data/admin credential,
failed Compose down, failed revocation/retry, interruption after revocation,
completed-removal retry, enrollment mismatch, malformed/unauthenticated
credentials and reused-root protection. Existing fixture tests are preserved.

Additional focused tests reject the default root, legacy second-based roots,
future roots and caveated credentials even with matching broker enrollment,
before any Docker command or revocation. Windows amd64 validation also passed
`go test -p 1 ./...` and `go vet -p 1 ./...` with Go 1.26.0.

UI build passed (existing large-bundle warning). Actual AppStore browser test in
headless Edge passed EN/PT at desktop/mobile widths, both app-specific notices,
install confirmation, unchanged BTCPay notice and zero API mutations.

The authorized regtest-only fixture VM `los-disposable-0555-lndg` was cloned
from the powered-off template, configured with 6 GiB RAM / 4 vCPUs and started
headless. Its UUID is `091d7dee-2f70-4d4c-8ca2-0d794d9e926f`, MAC
`08:00:27:D9:BE:F2`. The owner supplied its IP; both MAC and the previously
trusted template SSH identity were verified. No network scan was performed.
Ubuntu 24.04 amd64, native Bitcoin 31.2 and LND 0.21.6-beta were provisioned
using the dedicated regtest scripts, without production wallets or credentials.

`TestLNDgNativeRegtestCredentialLifecycle` initially **failed** on Linux:
the new enrollment check incorrectly required GID 0, although the existing
broker deliberately creates its credential snapshot as root:1000, mode 0640.
The fix validates this exact ownership/mode instead of weakening the generic
private-file predicate. The unchanged native regression test then **passed**:

- A copied dedicated credential authenticated before removal and was rejected
  by a real GetInfo RPC after removal.
- A newly baked root authenticated and could be removed again.
- A separate app credential and all pre-existing root IDs remained valid/present.
- Native TLS certificate/key, LND config and admin macaroon stayed byte-identical.
- Dry-run did not revoke; native Bitcoin and all three lab LNDs remained synced.

This test opts in with `LOS_LNDG_REGTEST=1`, checks the fixed lab marker/hostname
and actual LND network before mutations, and cleans up only its own test roots.
**Docker commands are recorded, not executed in this test.** It validates real
credential revocation, not installation/reinstallation of the LNDg container or
the production App Store UI. The complete focused LNDg test set also passed on
Linux as root (`-test.run 'TestLNDg|TestLndg'`).

An attempted full privileged-package Linux run is **not a pass**: the standalone
test binary lacks source-relative shell/template fixtures and the fresh lab lacks
the fixed Loop service account. Failures named these absent files/account; the
focused LNDg tests do not depend on those prerequisites. Do not treat that run as
full Linux regression coverage. The VM was shut down normally via ACPI after
testing and verified `poweroff`; disks and records were preserved. LOS-TEST2
remained running. Final Windows `go test -p 1 ./...` and `go vet -p 1 ./...`
also completed successfully after the enrollment ownership correction.

The equivalent LNbits enrollment ownership predicate was flagged on draft
PR #395 for its own native reproduction/correction; the assisted migration on
LOS-TEST2 does not validate that new automatic broker path.

## Required before removing draft

### LOS-TEST2 assisted Docker baseline (2026-11-08)

The owner explicitly authorized non-financial App Store lifecycle tests on
LOS-TEST2. Before changing runtime binaries, installation was attempted through
the authenticated Store API on the existing **0.5.54-Beta** Manager/broker.
LNDg was initially absent, with retained PostgreSQL/app data. A private on-node
backup was made; an isolated, network-disabled PostgreSQL container inspected
a separate copy. Auto Rebalance, Autopilot, Auto Fees and payment cleanup were
disabled, and the pending rebalance queue was empty. The review container was
stopped. Existing Docker RPC configuration and TLS already covered LNDg.

The baseline install failed with HTTP 500, `LNDg image app unavailable: app
image preparation failed`. The image-build journal identified the cause:
`Service reached runtime time limit` / `Failed with result 'timeout'` after
dependency installation. The existing build uses `RuntimeMaxSec=10min` in
`internal/privileged/lndg.go`. This is a **pre-existing baseline failure**, not
a demonstrated regression of the candidate. Do not infer that extending the
limit is sufficient until the full build and runtime checks pass.

Candidate binaries/UI were staged but **not deployed**. Final checks: UI still
0.5.54-Beta; native LND retained PID 3140; TLS/key/config/admin unchanged; all
1,423 original app-data files matched the backup; Manager and broker socket
active; LNbits running. No LNDg containers were created. The failed installation
left a catalog declaration, so the Store reports LNDg as installed/stopped.
The retained declaration/data allow a controlled retry. No payments, channel
operations, LND restart or Bitcoin changes were performed. Private backups and
the stopped review container remain on the node. Full lifecycle testing remains
blocked on the baseline image-build timeout.

- Native Linux Docker + LND fresh install, stop/start and uninstall/reinstall.
- Prove old copied credential fails and fresh credential works after reinstall.
- Preserve pre-existing database, app settings, TLS and other app roots.
- Real failure/retry with LND unavailable, failed Docker down, interrupted
  revocation/cleanup and incomplete prior installation/enrollment.
- Supported old UI upgrade and consistent Manager/broker deployment.
- Native architecture checks as applicable; no ARM pass claimed.

Permission-by-RPC reduction remains a separate investigation. Inventory all
calls (including optional tools, migrations, WalletKit and watchtower) and verify
functional parity in regtest before changing the policy. Never run financial
permission tests against LOS-TEST2 or production funds.

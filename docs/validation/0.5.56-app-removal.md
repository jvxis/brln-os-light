# 0.5.56-Beta App Store removal validation

PR #414, source `5f438753a60bf37ee748834ebb75487cec01b588`.
Validated in the complete four-PR candidate `7617a87768862b5877581e4543c5a975275d3864`
on 2026-11-13. No production code was changed during this validation.

## Baseline and native execution

Authorized Ubuntu 24.04.3 amd64 disposable `los-disposable-0555-tor-existing`,
UUID `e1677ec6-e12f-48c5-8f5b-76bb63089ff7`; exact MAC and approved SSH identity
checked before access. This is an existing-node fixture, not LOS-TEST2. Docker
29.1.3 and Compose 2.40.3 were installed after an APT simulation confirmed no
package removals. Native LND/Tor process identities and configuration/TLS hashes
were unchanged. Only one disposable ran.

Five stopped legacy-declaration scenarios were prepared with synthetic inputs,
isolated empty persistent-data sentinels and actual Docker orphan resources:
BTCPay (2.4.4 image in the former declaration), Electrs, Mempool, RoboSats and
CPU Miner (readable stale catalog declarations). No app workloads, blockchain
indexing, mainnet payments or channels were started. Synthetic credentials and
generated fixture keys were not production material.

- Original installed 0.5.55 Manager/broker: every stale declaration was refused
  through the authenticated uninstall API, leaving the resource intact.
- Installed candidate Manager/broker: normal authenticated HTTPS, CSRF and
  explicit uninstall confirmation reached the real restricted Manager, Unix
  socket broker and Docker Compose `down --remove-orphans` for all five apps.
  Each request returned HTTP 200, removed its managed declaration and Docker
  resource, retained its persistent-data sentinel, and passed repeated removal.
- Docker image inventory was identical before/after each removal: no image pull
  was needed. Existing secret-input hashes were unchanged before each request;
  focused tests also check byte preservation at the broker invocation boundary.
- The first orphan fixture omitted Compose's config-hash label, so Compose did
  not recognize it despite successful app removal. That harness assertion failed;
  exact empty synthetic resources were inspected/recreated with the required
  label and the five scenarios passed. No product validation was loosened.
- A genuine native LND credential with the former LNbits permission set was
  created only in this zero-fund fixture. Actual LNbits Start returned HTTP 409
  with `lnbits_credential_enrollment_missing`. Credential bytes/root set stayed
  unchanged, no container started and no secret appeared in the response.
  Only the newly created test root was retired afterward; original roots stayed
  unchanged. Initial fixture-only directory ownership was corrected after a
  permission-denied response before credential migration; that failed setup is
  not represented as a passing product test.

Logs and fixture executors remain in `/var/lib/los0556-release-validation` and
the operator's task cache. Native files/processes and broker self-test passed
after the real API scenarios. The disposable must be shut down normally after
the remaining release work, retaining its disk and evidence.

## Automated and UI checks

- Windows amd64 full `go test -p 1 ./...` and `go vet -p 1 ./...`: passed with
  bounded Go memory/concurrency. Initial concurrent compilation exhausted host
  memory and failed; that attempt is not a test pass.
- Ubuntu amd64 full Go tests and vet: passed. The first root test run exposed
  an unchanged LNDg unit-test assumption that the host's default channel.db does
  not exist. Both its test and implementation are unchanged from 0.5.55. The
  successful run masked `/data/lnd` only in a private child mount namespace for
  unit tests; native LND and subsequent real API tests used the original path.
- UI production build: passed after limiting memory/serializing work; initial
  concurrent Vite build failed allocating WebAssembly memory. Existing large
  chunk warning remains.
- Actual Edge/AppStore component, EN/PT desktop/mobile: catalog mismatch,
  missing enrollment and unavailable LND errors display their translated text,
  not raw broker detail. Screenshot visually inspected. Synthetic browser
  transport is distinguished from the real Linux API execution above.
- Focused regressions in this PR already demonstrate failure-before/pass-after
  for Manager declaration refresh and fixed broker codes. Strict broker catalog
  equality and generic refusal behavior remain covered; no security bypass.

## Limits

No native ARM or full new-install/install_existing installer matrix was repeated:
installer/toolchain requirements did not change. The five native removal tests
cover stopped legacy declarations with real Docker resources, not running full
BTCPay/Electrs/Mempool/RoboSats/mining workloads or end-to-end app functionality.
Existing safety/revocation tests remain applicable. Fedimint credential-bearing
declarations are intentionally not rewritten; the clear mismatch error is the
supported result. No general privileged file-writing capability was added.

# 0.5.57 — remove startup-critical default LND peers

Tracks [#421](https://github.com/jvxis/brln-os-light/issues/421) and upstream
[lightningnetwork/lnd#11582](https://github.com/lightningnetwork/lnd/issues/11582).

## Evidence and scope

The native LOS template included two fixed `addpeer` values. In
[LND 0.21.8-beta's startup loop](https://github.com/lightningnetwork/lnd/blob/v0.21.8-beta/server.go#L2620-L2655),
`ConnectToPeer` errors return a startup failure, including an already-connected
peer. The listener accepts connections before that loop. This supports the
reported inbound connection race, but is not a claim that an isolated native
reproduction of that race has passed.

This change removes those two defaults from `templates/lnd.conf` and disables
their exact legacy values in installed configs when the **new Manager starts**.
Using Manager startup is intentional: an older supported updater also starts
the new Manager, even though its old shell helper knows nothing of this fix.
No new shell-upgrade hook, broker operation, RPC permission or package is needed.

## Migration behavior and preserved boundaries

- Match only the two complete legacy `pubkey@onion:port` values in application
  options (or unsectioned root options), including duplicates/quoted values.
  Preserve different peers, different endpoints/ports, commented entries,
  unrelated sections and `gossip.pinned-syncers`.
- Existing and native origins need not be guessed from Bitcoin. An existing
  config without those exact values is byte-for-byte untouched; no migration
  directory or completion record is created in that case.
- A full original backup is atomically published in
  `/var/lib/lightningos/lnd-config-migrations/`: directory `0700`, backup and
  completion files `0600`. **Backups contain configuration credentials. Never
  include them in logs, an issue, an attachment or a public diagnostic bundle.**
- Only after the backup is durable, replace the first key byte of each matched
  `addpeer` with `#` (`#ddpeer=...`). This deliberately keeps file size and all
  other byte offsets unchanged. Do not rewrite/truncate/replace the config or
  change its owner, group, inode, mode or ACL. Preserve CRLF/LF and final-newline
  choices. The original exact text remains available in the private backup.
- A process interruption after one comment byte leaves a valid config with
  the other peer still active; the next run can complete it. Atomic temporary
  backup publication prevents a partially written backup being mistaken for a
  completed new backup. Unexpected pre-existing backup state fails closed.
- A per-config completion record prevents undoing an operator's deliberate
  later reintroduction after migration. That choice remains subject to the
  upstream startup behavior; this is not a general upstream fix for all peers.
- Keep directory mappings used by `install_existing` (`/data/lnd` pointing at
  its actual directory). An individually symlinked config, unsafe backup state,
  unreadable/unwritable file, stale read or unsupported config is deferred for
  review, without changing permissions or failing Manager startup.
- Take the existing LND config mutation mutex before concurrent Manager
  initializers. Revalidate file identity/content before sparse writes and verify
  the final bytes. Failures are logged generically, without private values.
- **Do not restart/stop LND, Bitcoin or Tor, disconnect peers, move funds or
  regenerate TLS.** The cleanup takes effect at the next normal LND restart.
  Existing channels/connections continue normally. No background forced-peer
  connection mechanism is added.

## Validation performed

Platform: Windows/amd64. Base: `3812f34547b53ddaaea00458c7dad08dd32f0def`.

Before editing:

```text
go test -p 1 ./internal/server -run 'LNDConfig|LNDNetwork|Upfront|Installer' -count=1
PASS
```

The new `TestLNDTemplateDoesNotRequireBootstrapPeersAtStartup` failed on the
original template, finding both active startup peers; it passes after the fix.

Functional temporary-file/byte-level regressions cover:

- Exact matches, root/application sections, duplicate values, quotes/spacing,
  CRLF/LF, no final newline, custom endpoints/ports and inactive comments.
- Original backup contents, sparse-byte-only changes, file identity/mode,
  idempotence and respecting later operator choices after completion.
- Missing config, no defaults and already-commented configs without writes.
- Cancellation, oversized/unsafe config, unavailable or incomplete backup,
  symlinked migration state and individually linked config refusal.
- Supported existing-node directory links (on platforms permitting symlinks).
- Injected interruption after the first sparse patch, preserved valid remaining
  config and successful retry; stale/unrelated writes and false-success refusal.
- Startup wiring independent of a new updater, and no service/peer execution
  imports/calls. These structural checks supplement, not replace, native tests.

Commands:

```text
go test -p 1 ./internal/server -run 'LNDBootstrap|DisableLegacyLNDBootstrap|LNDTemplate|LNDConfig|Installer' -count=1
go test -p 1 ./...
go vet -p 1 ./...
```

The commands passed on Windows/amd64. Linux-only tests were not executed there;
symlink cases remain subject to the host's ability to create links. POSIX
ownership, filesystem durability and permission-denial checks still require
the native Linux validation below.

No UI or public API contract changes. Existing config editing/reauthentication,
save/apply/rollback, installer and privilege-boundary suites remain in scope.

these local tests. Permission to reuse an isolated disposable has been requested.

Before marking ready:

1. Run the added Linux tests as an unprivileged user. Verify UID/GID/inode/mode
   preservation and actual read-only permission denial; root skips the latter
   and therefore cannot substitute for that check.
2. Run native amd64 new-install and existing-install scenarios. Confirm the new
   native template boots/discovers peers without these defaults, while existing
   custom config, links, permissions and RPC credentials remain unchanged.
3. Start with a supported old installed Manager and its **actual** UI updater;
   verify installing the candidate triggers the new Manager's migration, retains
   private backups and completion state, and leaves LND service identity/TLS
   unchanged. Running a candidate migration helper alone is not this transition.
4. In regtest only, exercise the relevant restart/reconnection behavior,
   unavailable prerequisites, interrupted migration and retry. Never use a
   funds-bearing node to reproduce the fatal startup race.
5. The corresponding native arm64 installation/runtime path has not been run.

Windows tests, source inspection and any cross-compilation are not Linux or
arm64 integration validation. Skipped tests must not be reported as passed.
